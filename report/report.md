## 3. Уточняющие вопросы к автору

Без ответов на эти вопросы нельзя однозначно реализовать или протестировать требования. Порядок: по важности.

**Q-01.** Ф-3 и Ф-4: если push в этом месяце уже отправлен по старому порогу, а клиент повысил порог, отправляется ли второй push при достижении нового порога? *Кому: бизнес.*
> «На карту приходится максимум один такой push за календарный месяц.» (строка 39 (Требования к изменениям / Функциональные требования))
> «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.» (строка 40 (Требования к изменениям / Функциональные требования))
- Что блокирует: Без ответа нельзя написать тест-кейс «смена порога после отправленного push». Разработчик не знает, сбрасывать ли признак отправки при сохранении настройки.
- Варианты: (а) Да: изменение порога сбрасывает признак отправки, Ф-4 — исключение из лимита Ф-3; (б) Нет: лимит Ф-3 абсолютный, после смены порога push в этом месяце не отправляется; (в) Да, но только если порог повышен; при понижении или сохранении того же значения признак не сбрасывается
- Рекомендация агента: Первый вариант: так Ф-4 работает буквально («независимо от истории»), а лимит Ф-3 действует внутри одной настройки. Тогда в Ф-3 нужно явно оговорить это исключение.
- Закрывает замечания: D-01, D-18

**Q-02.** Ф-2 и критерий приёмки 2: покупка 31 января в 23:58, проведена 1 февраля в 00:03. В какой месяц она попадает? *Кому: бизнес.*
> «Месяц определяется по дате совершения покупки в Алматы.» (строка 38 (Требования к изменениям / Функциональные требования))
> «Февральский счётчик вырос на 4 000 ₸» (строка 64 (Часть A. Новый функционал / Критерии приемки))
- Что блокирует: Не определено, какой временной атрибут события брать (авторизация или проведение). Критерий приёмки 2 противоречит Ф-2, поэтому его нельзя ни пройти, ни провалить.
- Варианты: (а) В январь: дата и время авторизации в часовом поясе Asia/Almaty; критерий 2 исправить на январский счётчик; (б) В февраль: дата проведения (клиринга) в Asia/Almaty; Ф-2 переписать
- Рекомендация агента: Январь по дате авторизации в Asia/Almaty: так совпадает с формулировкой Ф-2 и с ожиданием клиента. Критерий 2 нужно исправить.
- Закрывает замечания: D-03, D-14

**Q-03.** Часть B, REST type: сохранение настройки выполняется методом GET с параметрами в строке запроса. Заменяем его на POST/PUT с JSON-телом? *Кому: архитектор.*
> «Сохранение порога. Функциональные требования: чтение порога» (строка 103 (Часть B. REST API / Общие параметры))
> «curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data 'cardId=demo-42&amount=50000&enabled=1'» (строка 109 (Часть B. REST API / Общие параметры))
- Что блокирует: Нельзя реализовать контроллер и клиентский вызов. GET с изменением состояния кешируется и повторяется прокси, а cardId попадает в логи URL.
- Варианты: (а) PUT /alerts/limit с JSON-телом {cardId, amount, enabled}; (б) POST /alerts/saveLimit с JSON-телом; (в) Оставить GET с query-параметрами
- Рекомендация агента: PUT с JSON-телом: операция идемпотентно заменяет настройку (правило 2 части B), и Content-Type application/json станет осмысленным.
- Закрывает замечания: D-04, D-50

**Q-04.** Требования к интеграции и UI: экран показывает текущий порог, переключатель и сумму за месяц, а в части B есть только метод сохранения. Добавляем в часть B отдельный метод чтения? *Кому: аналитик.*

- Что блокирует: Нельзя реализовать открытие экрана в приложении. Не определён источник суммы за месяц для тест-кейса отображения.
- Варианты: (а) Да: GET /alerts/limit?cardId возвращает amount, enabled и сумму расходов за текущий месяц; (б) Да, два метода: чтение настройки отдельно, сумма расходов из сервиса расходов отдельно; (в) Нет: чтение описывается в другом документе (указать какой)
- Рекомендация агента: Первый вариант: один вызов при открытии экрана, все данные экрана из одного контракта.

**Q-05.** Часть B, статусы 200/ERROR и 400: amount вне диапазона 1 000–1 000 000 возвращает HTTP 400 или HTTP 200 с result=ERROR? *Кому: аналитик.*
> «Ответ в случае, если параметры запроса заполнены неверно.» (строка 163 (Часть B. REST API / Статусы))
> «При отклонении суммы вернуть прежнее состояние и результат ERROR.» (строка 121 (Часть B. REST API / Логика работы метода))
- Что блокирует: Нельзя написать проверки ответа API для граничных значений 999 и 1 000 001. Приложение не знает, по какому признаку показывать сообщение под полем.
- Варианты: (а) 400 с телом {result: ERROR, message} для любых невалидных параметров; 200 только при успехе; (б) 200 с result=ERROR при бизнес-отказе по сумме, 400 только для синтаксических ошибок (нет параметра, не число, enabled≠0/1)
- Рекомендация агента: Второй вариант: он сохраняет оба описанных в документе ответа. Нужно лишь явно развести бизнес-валидацию и синтаксическую ошибку.

**Q-06.** Ф-2 и Ф-3: порог 50 000, push отправлен, возврат опустил расходы ниже порога, новая покупка снова его превысила. Отправляется ли повторный push в этом месяце? *Кому: бизнес.*
> «Возврат уменьшает расходы месяца исходной покупки.» (строка 38 (Требования к изменениям / Функциональные требования))
> «Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент получает push.» (строка 39 (Требования к изменениям / Функциональные требования))
- Что блокирует: Без ответа нельзя написать тест-кейс «возврат после push → повторное пересечение». Разработчик не знает, сбрасывает ли возврат признак отправки.
- Варианты: (а) Нет: признак отправки за месяц не сбрасывается возвратом, лимит Ф-3 приоритетен; (б) Да: возврат ниже порога сбрасывает признак отправки
- Рекомендация агента: Нет: иначе серия покупок и возвратов вызывает спам-уведомления. Первое предложение Ф-3 нужно дополнить условием «если push в этом месяце ещё не отправлялся».
- Закрывает замечания: D-16, D-15

**Q-07.** Ф-1 и Требования к данным: учитываются ли покупки в счётчике месяца, пока уведомление выключено? *Кому: бизнес.*
> «Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸ включительно. По умолчанию уведомление выключено.» (строка 37 (Требования к изменениям / Функциональные требования))
- Что блокирует: Нельзя спроектировать момент начала накопления. Нельзя написать тест «включение в середине месяца при сумме выше порога». Неясна предусловная часть критериев приёмки 1 и 3.
- Варианты: (а) Да: счётчик ведётся всегда; если при включении сумма уже не ниже порога, push в этом месяце не отправляется; (б) Да: счётчик ведётся всегда; если при включении сумма уже не ниже порога, push отправляется сразу; (в) Нет: счётчик стартует с момента включения
- Рекомендация агента: Первый вариант: экран показывает полную сумму за месяц, а push остаётся строго событием перехода «снизу вверх», как в Ф-3.

**Q-08.** Требования к интеграции: по какому ключу событие процессинга считается повторной доставкой? *Кому: архитектор.*

- Варианты: (а) По идентификатору операции процессинга; (б) По паре «идентификатор операции + тип (покупка/возврат)»; (в) По идентификатору сообщения в шине
- Рекомендация агента: Пара «идентификатор операции + тип»: возврат может нести идентификатор исходной покупки, а поле идентификатора операции уже есть в модели данных.

## 8. Итог

**Можно ли начинать разработку и тестирование: Нет.** Начинать разработку и тестирование нельзя: 5 критичных дефектов (противоречия, непроверяемые или неполные требования). Сначала исправить их и ответить на уточняющие вопросы.

Что исправить в первую очередь:

1. **D-01** (строка 40 (Требования к изменениям / Функциональные требования)): Противоречие с Ф-3: «максимум один такой push за календарный месяц». Если push уже отправлен по старому порогу, Ф-4 требует нового push после повышения порога, а Ф-3 его запрещает. Также: Ф-4 требует push «независимо от истории предыдущей настройки», то есть второй push в месяце после смены порога. Это противоречит Ф-3: максимум один push в месяц на карту. API-правило не указывает, какое требование главнее. Исправление: Выбрать одно правило и согласовать с владельцем продукта. Например: «При изменении порога признак отправки за текущий месяц сбрасывается, и при последующем достижении нового порога отправляется push. Значит, расти должен январский счётчик, а не февральский. Критерий приёмки фактически определяет месяц по дате проведения. Исправление: Исходные условия: покупка совершена 31 января в 23:58 по Алматы на 4 000 ₸. Действие: покупка проведена 1 февраля в 00:03 по Алматы. Ожидаемый результат: январский счётчик вырос на 4 000 ₸, февральский не изменился.
3. **D-02** (строка 52 (Часть A. Новый функционал / Требования к интеграции)): В части B описан только метод сохранения /alerts/saveLimit. Метода чтения настройки и суммы за месяц, которую по строке 29 нужно показать на экране, нет. Также: Описание метода противоречит само себе: заявлено и сохранение, и чтение. URL saveLimit и логика (строка 120) говорят о сохранении, а «функциональные требования» — о чтении. Исправление: Добавить в часть B метод GET /alerts/limit?cardId=… с ответом: признак включения, порог в тенге, расходы текущего месяца в тенге.
4. **D-05** (строка 163 (Часть B. REST API / Статусы)): Для amount вне диапазона 1 000–1 000 000 возможны два ответа: 400 (строка 163) или 200 с result=ERROR «Проверьте сумму» (строка 171). Значение вне 1 000–1 000 000 → 200 {result:"ERROR", message:"Проверьте сумму"}. Нечисловое значение или отсутствие параметра → 400.
5. **D-04** (строка 104 (Часть B. REST API / Общие параметры)): Метод GET используется для операции записи (сохранение настройки), параметры передаются в строке запроса. Это фиксирует небезопасное решение: идентификатор попадёт в логи прокси и историю запросов. Исправление: Использовать POST или PUT с телом запроса для сохранения.
