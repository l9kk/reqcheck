## 3. Уточняющие вопросы к автору

Без ответов на эти вопросы нельзя однозначно реализовать или протестировать требования. Порядок: по важности.

**Q-01.** В НФТ-03 указано логирование чувствительных данных карт. Как соответствовать требованиям безопасности PCI DSS при логировании запросов к агрегатору? *Кому: ИБ.*
> «НФТ-03. Все запросы к агрегатору логируются полностью, включая номер карты и CVV, для разбора спорных» (строка 47 (ТЗ: Автопополнение баланса мобильного телефона / 4. Нефункциональные требования))
- Что блокирует: Проектирование сервиса логирования и прохождение аудита ИБ.
- Варианты: (а) Маскировать номер карты и полностью исключить CVV из логов; (б) Логировать только ID транзакции без данных карты
- Рекомендация агента: Маскировать номер карты и полностью исключить CVV из логов для соблюдения требований PCI DSS.
- Закрывает замечания: D-04

**Q-02.** В разделе 5 для списания средств указан метод GET без ключа идемпотентности. Какой HTTP-метод и заголовок защиты от повторных списаний следует использовать? *Кому: архитектор.*
> «\| GET \| /v1/payment?msisdn=&amount= \| Платёж в пользу оператора \|» (строка 55 (ТЗ: Автопополнение баланса мобильного телефона / 5. Интеграция с агрегатором))
- Что блокирует: Разработка интеграционного API с агрегатором и защита от двойных списаний.
- Варианты: (а) Использовать POST с передачей idempotency_key в заголовке; (б) Использовать PUT с уникальным transaction_id в URI
- Рекомендация агента: Использовать POST с передачей idempotency_key в заголовке согласно стандартам REST API.
- Закрывает замечания: D-05, D-06

**Q-03.** В ТР-03 установлен лимит 3 пополнения за сутки, а в критерии 3 выполняется четвёртое пополнение. Какое ограничение на количество автопополнений в сутки должно соблюдаться? *Кому: бизнес.*
> «За календарные сутки выполняется не более трёх автопополнений одного номера.» (строка 28 (ТЗ: Автопополнение баланса мобильного телефона / 3. Функциональные требования))
> «\| 3 \| Выполнено 3 пополнения за сутки \| Баланс снова ниже порога \| Выполняется четвёртое пополнение \|» (строка 66 (ТЗ: Автопополнение баланса мобильного телефона / 6. Критерии приёмки))
- Что блокирует: Тестирование и разработка логики проверки суточного лимита автопополнений.
- Варианты: (а) Строго не более 3 пополнений за сутки; (б) Снять ограничение на количество пополнений
- Рекомендация агента: Строго не более 3 пополнений за сутки для защиты от фрода и спама списаний.
- Закрывает замечания: D-03

**Q-04.** В ТР-02 проверка выполняется раз в сутки, что противоречит ТР-03 и цели сервиса. С какой периодичностью и в каком часовом поясе нужно запрашивать баланс? *Кому: аналитик.*
> «Система раз в сутки запрашивает у агрегатора баланс номера. Если баланс ниже порога, система списывает сумму» (строки 25-26 (ТЗ: Автопополнение баланса мобильного телефона / 3. Функциональные требования))
> «За календарные сутки выполняется не более трёх автопополнений одного номера.» (строка 28 (ТЗ: Автопополнение баланса мобильного телефона / 3. Функциональные требования))
- Что блокирует: Настройка планировщика проверки баланса и реализации логики регулярного опроса.
- Варианты: (а) Каждые 4 часа по времени UTC+5; (б) Раз в час по времени UTC+5
- Рекомендация агента: Каждые 4 часа по времени UTC+5 для своевременного автопополнения без перегрузки агрегатора.

**Q-06.** В ТР-04 указано повторное списание «через некоторое время». По какому расписанию и сколько раз нужно повторять попытки списания при нехватке средств на карте? *Кому: аналитик.*
> «ТР-04. Если на карте недостаточно средств, система повторяет списание через некоторое время.» (строка 30 (ТЗ: Автопополнение баланса мобильного телефона / 3. Функциональные требования))

- Рекомендация агента: 3 попытки с интервалом 1 час для быстрого восстановления связи после пополнения карты.

- Рекомендация агента: Push с фолбеком на SMS при ошибке доставки для оптимизации расходов на SMS.

- Guard: дубликат. Формулировка «через некоторое время» является неопределенной и допускает разные трактовки.
- Critic: объединено с D-20. Формулировка содержит слова, которые нельзя проверить однозначно: «максимально» (превосходная степень), «быстро» (размытое наречие или прилагательное).

- Critic: объединено с D-04. Требование хранить CVV в логах нарушает стандарты безопасности PCI DSS и создает критическую уязвимость.
