Критичные дефекты:

- **D-01** (Полное (29148 5.2.5); строка 38 (Требования к изменениям / Функциональные требования)): Не описано поведение системы, если возврат за покупку прошлого месяца происходит в текущем месяце: пересчитывается ли статус отправки push за прошлый месяц и отправляется ли повторный push при новой покупке в текущем месяце.
- **D-02** (Согласованность набора (29148 5.2.6); строка 39 (Требования к изменениям / Функциональные требования)): Прямое противоречие между Ф-3 и Ф-4: Ф-3 строго ограничит отправку одним push в месяц на карту, а Ф-4 требует отправить push при повторном достижении нового порога 'независимо от истории предыдущей настройки'. В сценарии, когда в текущем месяце push уже отправлялся, а клиент затем повысил порог и снова достиг его, выполнимость обоих правил одновременно невозможна.
- **D-03** (Полное (29148 5.2.5); строка 40 (Требования к изменениям / Функциональные требования)): Не указано, что происходит, если клиент устанавливает новый порог МЕНЬШЕ текущей накопленной суммы расходов за месяц (например, расходы 50 000 ₸, а новый порог 40 000 ₸). Отправляется ли push сразу, при следующей покупке или не отправляется вовсе.
- **D-04** (Корректное (29148 5.2.5); строка 64 (Часть A. Новый функционал / Критерии приемки)): Прямое противоречие требованию Ф-2 (R-06), в котором указано: «Месяц определяется по дате совершения покупки в Алматы». Совершение было 31 января (январь), но в критерии приёмки сумма зачисляется в февраль.
- **D-05** (Корректное (29148 5.2.5); строки 103-104 (Часть B. REST API / Общие параметры)): Метод сохранения данных `/alerts/saveLimit` использует HTTP GET вместо POST/PUT. Кроме того, в описании метода указано «Сохранение порога», а рядом — «чтение порога».
- **D-06** (Полнота набора (29148 5.2.6); строка 103 (Часть B. REST API / Общие параметры)): В части A и в описании метода части B заявлена необходимость чтения порога мобильным приложением, однако в спецификации REST API полностью отсутствует описание метода GET для чтения текущих настроек (описаны только параметры для сохранения).
- **D-07** (Корректное (29148 5.2.5); строка 151 (Часть B. REST API / Ответ)): Утверждение ошибочно: статус 201 не используется в спецификации метода, а при коде 200 спецификация допускает ответ с результатом ошибки (result: ERROR).

## 3. Уточняющие вопросы к автору

Без ответов на эти вопросы нельзя однозначно реализовать или протестировать требования. Порядок: по важности.

**Q-01.** В Ф-3 указано «На карту приходится максимум один такой push за календарный месяц», а в Ф-4 — «следующее достижение вызывает push независимо от истории предыдущей настройки». Как должна вести себя система, если клиент изменил порог и снова достиг его в том же месяце, где push уже отправлялся? *Кому: бизнес.*
> «На карту приходится максимум один такой push за календарный месяц.» (строка 39 (Требования к изменениям / Функциональные требования))
- Что блокирует: Разработка логики проверки отправки push в сервисе расходов и интеграционные тест-кейсы смены настройки в одном месяце.
- Варианты: (а) Изменение порога сбрасывает счетчик push и разрешает повторную отправку в текущем месяце; (б) Правило «максимум 1 push в месяц» строго приоритетно, повторный push не отправляется ни при каких условиях
- Рекомендация агента: Изменение порога сбрасывает счетчик push, так как иначе условие Ф-4 о независимости от истории настройки невыполнимо.
- Закрывает замечания: D-02, D-03, D-13

**Q-02.** В спецификации REST API метод сохранения настроек указан как HTTP GET (`/alerts/saveLimit`), а метод чтения настроек отсутствует. Какова целевая структура REST API для управления настройками порога? *Кому: архитектор.*
> «Сохранение порога. Функциональные требования: чтение порога» (строка 103 (Часть B. REST API / Общие параметры))
- Что блокирует: Проектирование контроллера AlertsController, разработка клиент-серверного взаимодействия и автотесты API.
- Варианты: (а) Разделить на dwa метода: POST/PUT /alerts/threshold для сохранения и GET /alerts/threshold для чтения; (б) Выделить POST /alerts/saveLimit для сохранения и GET /alerts/getLimit для чтения
- Рекомендация агента: Разделить на два метода: POST/PUT /alerts/threshold для сохранения и GET /alerts/threshold для чтения согласно стандартам REST.
- Закрывает замечания: D-05, D-06, D-21

**Q-03.** Требование Ф-2 указывает, что возврат уменьшает расходы месяца исходной покупки. Как должна вести себя система, если возврат за покупку прошлого месяца проведен в текущем месяце и снизил расходы прошлого месяца ниже порога? *Кому: бизнес.*
> «Месяц определяется по дате совершения покупки в Алматы. В расходы входят проведённые покупки. Возврат уменьшает расходы месяца исходной покупки.» (строка 38 (Требования к изменениям / Функциональные требования))
- Что блокирует: Алгоритм перерасчета агрегатов за прошедшие периоды и логика проверки отправки уведомлений при возвратах.
- Варианты: (а) Пересчитать агрегат прошлого месяца без генерации каких-либо push-уведомлений; (б) Уменьшать расходы текущего месяца, в котором фактически проведен возврат в процессинге
- Рекомендация агента: Пересчитать агрегат прошлого месяца без отправки push, так как прошлый месяц уже завершен.
- Закрывает замечания: D-01

**Q-04.** В критерии приемки покупка от 31 января в 23:58, проведенная 1 февраля в 00:03, относит сумму к февралю, что противоречит Ф-2 («Месяц определяется по дате совершения покупки в Алматы»). По какой дате определяется месяц транзакции? *Кому: аналитик.*
> «Покупка 31 января в 23:58 на 4 000 ₸ \| Провести 1 февраля в 00:03 по Алматы \| Февральский счётчик вырос на 4 000 ₸» (строка 64 (Часть A. Новый функционал / Критерии приемки))
- Что блокирует: Реализация алгоритма группировки расходов по месяцам в карточном процессинге / сервисе расходов и сценарии приемки.
- Варианты: (а) По дате совершения покупки клиентом по времени Алматы (январь); (б) По дате проведения/клиринга операции в процессинге (февраль)
- Рекомендация агента: По дате совершения покупки клиентом по времени Алматы, в полном соответствии с требованием Ф-2.
- Закрывает замечания: D-04

**Q-05.** В спецификации API описаны противоречивые статусы (упоминаются коды 201 и 404, а при 200 OK допускается body с result: ERROR). Каковы единые правила формирования HTTP-статусов и структуры ошибок? *Кому: аналитик.*
> «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный.» (строка 151 (Часть B. REST API / Ответ))
- Что блокирует: Обработка ответов API на стороне мобильного приложения и реализация обработчика исключений на бэкенде.
- Варианты: (а) Использовать стандартные HTTP-коды (200 OK при успехе, 400 Bad Request при ошибке валидации, 404 Not Found при отсутствии карты); (б) Всегда возвращать HTTP 200 OK и передавать статус ошибки внутри поля result в JSON
- Рекомендация агента: Использовать стандартные HTTP-коды ответа (200, 400, 401, 404, 500), убрав result: ERROR из кода 200.
- Закрывает замечания: D-07, D-22, D-23, D-24, D-25, D-26

**Q-06.** В требованиях не указаны значение порога по умолчанию при первом включении уведомления, текст push-уведомления и передаваемая в него сумма. Каковы точные бизнес-требования к этим параметрам? *Кому: бизнес.*
> «Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸ включительно. По умолчанию уведомление выключено.» (строка 37 (Требования к изменениям / Функциональные требования))
- Что блокирует: Дизайн UI/UX экранов настроек, формирование шаблонов push-уведомлений и интеграционные тесты push-сервиса.
- Варианты: (а) Задать дефолтный порог 50 000 ₸, в push передавать значение порога и последние 4 цифры карты; (б) Сделать поле ввода порога обязательным при первом включении тумблера без дефолтного значения
- Рекомендация агента: Задать дефолтный порог 50 000 ₸ и утвердить единый текст push-сообщения.
- Закрывает замечания: D-11, D-12, D-14

**Q-07.** В требованиях к интеграции не описана обработка событий процессинга, поступивших не по порядку (out-of-order), и точка отсчета времени для SLA доставки push (1 минута). Как должны обрабатываться такие случаи? *Кому: архитектор.*
> «Повторная доставка одного события процессинга сохраняет исходный итог.» (строка 52 (Часть A. Новый функционал / Требования к интеграции))
- Что блокирует: Проектирование очереди сообщений, механизмов дедупликации и контроль SLA сервиса расходов.
- Варианты: (а) Сортировать события по timestamp операции, вести отсчет SLA 1 мин от момента получения события сервисом расходов; (б) Обрабатывать события строго по порядку поступления в очередь, отсчитывать SLA от времени транзакции в процессинге
- Рекомендация агента: Упорядочивать события по timestamp операции и отсчитывать SLA от момента приема события сервисом расходов.
- Закрывает замечания: D-17, D-27

**Q-08.** На Sequence Diagram отсутствуют требования к авторизации и аутентификации при межсервисном взаимодействии. Какой протокол и механизмы защиты должны применяться? *Кому: ИБ.*
> «Процессинг → сервис расходов: проведена покупка. Сервис расходов → настройки: получить порог карты.» (строка 43 (Часть A. Новый функционал / Sequence Diagram))
- Что блокирует: Реализация межсервисной безопасности (Service-to-Service auth) и прохождение аудита ИБ.
- Варианты: (а) Использовать mTLS и m2m OAuth2/JWT токены между всеми микросервисами; (б) Ограничить доступ на сетевом уровне в закрытом контуре (VPC) с API-ключами
- Рекомендация агента: Использовать mTLS и m2m JWT-токены в соответствии со стандартами информационной безопасности банка.
- Закрывает замечания: D-15

## 8. Итог

**Можно ли начинать разработку и тестирование: Нет.** Начинать разработку и тестирование нельзя: 7 критичных дефектов (противоречия, непроверяемые или неполные требования). Сначала исправить их и ответить на уточняющие вопросы.

Что исправить в первую очередь:

1. **D-02** (строка 39 (Требования к изменениям / Функциональные требования)): Прямое противоречие между Ф-3 и Ф-4: Ф-3 строго ограничит отправку одним push в месяц на карту, а Ф-4 требует отправить push при повторном достижении нового порога 'независимо от истории предыдущей настройки'. В сценарии, когда в текущем месяце push уже отправлялся, а клиент затем повысил порог и снова достиг его, выполнимость обоих правил одновременно невозможна. Исправление: Уточнить правило Ф-3, указав исключение: 'максимум один push за календарный месяц, за исключением случая изменения порога согласно Ф-4'.
2. **D-04** (строка 64 (Часть A. Новый функционал / Критерии приемки)): Прямое противоречие требованию Ф-2 (R-06), в котором указано: «Месяц определяется по дате совершения покупки в Алматы». Совершение было 31 января (январь), но в критерии приёмки сумма зачисляется в февраль. Исправление: | Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Январский счётчик вырос на 4 000 ₸ |
3. **D-05** (строки 103-104 (Часть B. REST API / Общие параметры)): Метод сохранения данных `/alerts/saveLimit` использует HTTP GET вместо POST/PUT. Кроме того, в описании метода указано «Сохранение порога», а рядом — «чтение порога». Исправление: Изменить метод на POST или PUT для сохранения настроек порога. Разделять эндпоинты чтения (GET /alerts/limit) и сохранения (POST /alerts/saveLimit).
4. **D-06** (строка 103 (Часть B. REST API / Общие параметры)): В части A и в описании метода части B заявлена необходимость чтения порога мобильным приложением, однако в спецификации REST API полностью отсутствует описание метода GET для чтения текущих настроек (описаны только параметры для сохранения). Исправление: Добавить в Часть B спецификацию REST API метода получения настроек (например, GET /alerts/getLimit) с описанием формата ответа.
5. **D-03** (строка 40 (Требования к изменениям / Функциональные требования)): Не указано, что происходит, если клиент устанавливает новый порог МЕНЬШЕ текущей накопленной суммы расходов за месяц (например, расходы 50 000 ₸, а новый порог 40 000 ₸). Отправляется ли push сразу, при следующей покупке или не отправляется вовсе. Исправление: При изменении порога накопленная сумма сохраняется. Если новая сумма порога меньше или равна текущей накопленной сумме и push в этом месяце еще не отправлялся, push отправляется при совершении первой следующей покупки.
6. **D-01** (строка 38 (Требования к изменениям / Функциональные требования)): Не описано поведение системы, если возврат за покупку прошлого месяца происходит в текущем месяце: пересчитывается ли статус отправки push за прошлый месяц и отправляется ли повторный push при новой покупке в текущем месяце. Исправление: Возврат уменьшает сумму накопленных расходов месяца исходной покупки. Если в результате возврата расходы за прошлый месяц стали ниже порога, push за прошлый месяц повторно не отправляется.
7. **D-07** (строка 151 (Часть B. REST API / Ответ)): Утверждение ошибочно: статус 201 не используется в спецификации метода, а при коде 200 спецификация допускает ответ с результатом ошибки (result: ERROR). Исправление: Сформулировать правило: HTTP 200 с "result":"OK" считается успешным выполнением. Ошибки валидации вынести в HTTP 400.
