## 3. Уточняющие вопросы к автору

Без ответов на эти вопросы нельзя однозначно реализовать или протестировать требования. Порядок: по важности.

**Q-01.** Ф-3 и Ф-4: Отправлять ли повторный push в текущем месяце при увеличении порога, если клиент уже получал push на прежнем пороге? *Кому: бизнес.*
> «На карту приходится максимум один такой push за календарный месяц» (строка 39 (Требования к изменениям / Функциональные требования))
> «следующее достижение вызывает push независимо от истории предыдущей настройки» (строка 40 (Требования к изменениям / Функциональные требования))
- Что блокирует: Разработка логики проверки отправки push и тест-кейсы на изменение порога в текущем месяце.
- Варианты: (а) Отправлять push при достижении нового порога, так как настройка сбросила условие; (б) Не отправлять push, строго соблюдая ограничение 1 push в календарный месяц на карту
- Рекомендация агента: Отправлять push при достижении нового порога, так как сменена настройка
- Закрывает замечания: D-02

**Q-02.** Часть B, строки 104 и 147: Каким HTTP-методом и в каком формате должен реализовываться метод сохранения порога? *Кому: архитектор.*
> «\| REST type \| GET \|» (строка 104 (Часть B. REST API / Общие параметры))
> «Content-Type: application/json .» (строка 147 (Параметры запроса / Request body))
- Что блокирует: Проектирование REST API контроллера AlertsController и интеграционное тестирование.
- Варианты: (а) POST/PUT метод с передачей JSON в body; (б) PATCH метод с передачей параметров в query
- Рекомендация агента: POST/PUT метод с передачей JSON в body, так как GET не изменяет состояние
- Закрывает замечания: D-06, D-24

**Q-03.** Часть A и Часть B: Какой REST API метод должен быть описан для чтения настроек карты и накопленных расходов за месяц? *Кому: аналитик.*
> «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»» (строка 52 (Часть A. Новый функционал / Требования к интеграции))
- Что блокирует: Разработка UI-экрана мобильного банка и интеграционные тесты загрузки данных.
- Варианты: (а) GET /alerts/getLimit с возвратом limit_kzt, enabled и current_expenses; (б) GET /alerts/status с расширенной структурой данных
- Рекомендация агента: GET /alerts/getLimit с возвратом лимита, признака и расходов за месяц
- Закрывает замечания: D-04

**Q-04.** Ф-2 и критерий приёмки 2: В расходы какого месяца включать покупку от 31 января 23:58, если обработка в процессинге прошла 1 февраля? *Кому: аналитик.*
> «Месяц определяется по дате совершения покупки в Алматы» (строка 38 (Требования к изменениям / Функциональные требования))
> «Покупка 31 января в 23:58 на 4 000 ₸ \| Провести 1 февраля в 00:03 по Алматы \| Февральский счётчик вырос на 4 000 ₸» (строка 64 (Часть A. Новый функционал / Критерии приемки))
- Что блокирует: Расчёт агрегата месячных расходов и автоматизированные тесты транзакций на стыке месяцев.
- Варианты: (а) В январь по дате совершения покупки по времени Алматы; (б) В февраль по дате обработки события в процессинге
- Рекомендация агента: В январь, согласно основному требованию Ф-2
- Закрывает замечания: D-05

**Q-05.** Требование Ф-2: Нужен ли пересчёт расходов прошлого месяца и повторная отправка push при проведении возврата в текущем месяце? *Кому: бизнес.*
> «Возврат уменьшает расходы месяца исходной покупки» (строка 38 (Требования к изменениям / Функциональные требования))
- Что блокирует: Логика обработки событий возврата в сервисе расходов и тестирование сценариев с возвратами.
- Варианты: (а) Уменьшать расходы прошлого месяца без перерасчета и повторного push; (б) Уменьшать расходы и сбрасывать признак отправки push за прошлый месяц
- Рекомендация агента: Уменьшать расходы прошлого месяца без повторного push
- Закрывает замечания: D-01

**Q-06.** Требование Ф-4: Что происходит с отправкой push, если новый порог устанавливается ниже текущей накопленной суммы расходов за месяц? *Кому: бизнес.*
> «При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.» (строка 40 (Требования к изменениям / Функциональные требования))
- Что блокирует: Разработка триггеров отправки push при вызове метода сохранения настроек.
- Варианты: (а) Push не отправляется до наступления следующего месяца; (б) Push отправляется сразу в момент сохранения настройки; (в) Push отправляется при следующей покупке
- Рекомендация агента: Push не отправляется до следующего месяца, так как порог уже превышен
- Закрывает замечания: D-03

**Q-07.** Sequence Diagram и Ф-3: Каковы итоговый шаблон текста push-уведомления и правило выбора передаваемой суммы? *Кому: аналитик.*
> «Сервис расходов → push: передать последние четыре цифры карты и сумму при достижении порога.» (строка 43 (Часть A. Новый функционал / Sequence Diagram))
- Что блокирует: Интеграция с сервисом push-уведомлений и верстка push-сообщений.
- Варианты: (а) Передавать сумму накопленных расходов за месяц; (б) Передавать значение установленного порога
- Рекомендация агента: Передавать сумму накопленных расходов за месяц
- Закрывает замечания: D-14, D-15

**Q-08.** Часть B: Какое единое правило HTTP-статуса ответа применяется при ошибках валидации параметров в API? *Кому: архитектор.*
> «При отклонении суммы вернуть прежнее состояние и результат ERROR.» (строка 121 (Часть B. REST API / Логика работы метода))
> «Ответ в случае, если параметры запроса заполнены неверно.» (строка 163 (Часть B. REST API / Статусы))
- Что блокирует: Единый стандарт обработки ошибок валидации на backend и мобильном клиенте.
- Варианты: (а) Возвращать HTTP 400 Bad Request для всех ошибок валидации; (б) Возвращать HTTP 200 OK с result: ERROR для бизнес-ошибок
- Рекомендация агента: Возвращать HTTP 400 Bad Request для всех ошибок валидации по стандартам REST
- Закрывает замечания: D-22, D-27

**Q-09.** Требование Ф-1: Какое значение порога должно устанавливаться по умолчанию при первом включении уведомления в UI? *Кому: аналитик.*
> «Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸ включительно. По умолчанию уведомление выключено.» (строка 37 (Требования к изменениям / Функциональные требования))
- Что блокирует: UI-логика первоначального отображения экрана в мобильном приложении.
- Варианты: (а) Требовать обязательный ввод суммы пользователем перед включением; (б) Подставлять дефолтное значение 50 000 ₸
- Рекомендация агента: Подставлять значение 50 000 ₸ как наиболее популярный бюджет
- Закрывает замечания: D-11

**Q-10.** Нефункциональные требования: Каковы параметры retry и обработки ошибок при недоступности сервиса push? *Кому: архитектор.*
> «Сервис передаёт push на отправку в течение минуты после получения события.» (строка 46 (Часть A. Новый функционал / Нефункциональные требования))
- Что блокирует: Архитектурное проектирование очереди сообщений (MQ) и обработчиков сбоев.
- Варианты: (а) 3 попытки отправки с интервалом и последующей отправкой в DLQ; (б) Повторять попытки в течение 1 часа, затем отменять
- Рекомендация агента: 3 попытки отправки с сохранением в DLQ при ошибке
- Закрывает замечания: D-16

## 8. Итог

**Можно ли начинать разработку и тестирование: Нет.** Начинать разработку и тестирование нельзя: 7 критичных дефектов (противоречия, непроверяемые или неполные требования). Сначала исправить их и ответить на уточняющие вопросы.

Что исправить в первую очередь:

1. **D-06** (строка 104 (Часть B. REST API / Общие параметры)): Метод GET используется для операции записи (сохранение настройки), параметры передаются в строке запроса. Также: Метод сохранения данных `/alerts/saveLimit` использует HTTP GET вместо POST/PUT. Кроме того, в описании метода указано «Сохранение порога», а рядом — «чтение порога». Исправление: Использовать POST или PUT с телом запроса для сохранения.
2. **D-04** (строка 52 (Часть A. Новый функционал / Требования к интеграции)): В спецификации REST API (Часть B) отсутствует метод для чтения текущих настроек и накопленных расходов карты (GET-метод чтения), несмотря на то, что Часть A прямо обязывает мобильное приложение читать настройки и отображать порог и сумму за месяц на UI. Исправление: Дополнить Часть B спецификацией REST API метода получения настроек (например, GET /alerts/getLimit).
3. **D-02** (строка 39 (Требования к изменениям / Функциональные требования)): Противоречие между правилами Ф-3 и Ф-4: в сценарии, когда клиент уже получил push в текущем месяце (достигнув порога 50 000 ₸), а затем увеличивает порог до 70 000 ₸ и совершает покупку до 70 000 ₸, правило Ф-4 требует отправить push («независимо от истории»), а правило Ф-3 запрещает отправлять более одного push за календарный месяц. Исправление: Уточнить приоритет правил: разрешить отправку повторного push при явном увеличении порога клиентом или явно ограничить действие Ф-4 рамками общего месячного лимита в 1 push.
4. **D-05** (строка 64 (Часть A. Новый функционал / Критерии приемки)): Прямое противоречие требованию Ф-2 (R-06), в котором указано: «Месяц определяется по дате совершения покупки в Алматы». Совершение было 31 января (январь), но в критерии приёмки сумма зачисляется в февраль. Исправление: | Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Январский счётчик вырос на 4 000 ₸ |
5. **D-03** (строка 40 (Требования к изменениям / Функциональные требования)): Не указано, что происходит, если клиент устанавливает новый порог МЕНЬШЕ текущей накопленной суммы расходов за месяц (например, расходы 50 000 ₸, а новый порог 40 000 ₸). Отправляется ли push сразу, при следующей покупке или не отправляется вовсе. Исправление: При изменении порога накопленная сумма сохраняется. Если новая сумма порога меньше или равна текущей накопленной сумме и push в этом месяце еще не отправлялся, push отправляется при совершении первой следующей покупки.
6. **D-01** (строка 38 (Требования к изменениям / Функциональные требования)): Не описано поведение системы, если возврат за покупку прошлого месяца происходит в текущем месяце: пересчитывается ли статус отправки push за прошлый месяц и отправляется ли повторный push при новой покупке в текущем месяце. Исправление: Возврат уменьшает сумму накопленных расходов месяца исходной покупки. Если в результате возврата расходы за прошлый месяц стали ниже порога, push за прошлый месяц повторно не отправляется.
7. **D-07** (строка 151 (Часть B. REST API / Ответ)): Утверждение ошибочно: статус 201 не используется в спецификации метода, а при коде 200 спецификация допускает ответ с результатом ошибки (result: ERROR). Также заголовок содержит противоречивое наименование «Successful — Created» для статуса 200 (Created относится к коду 201).
